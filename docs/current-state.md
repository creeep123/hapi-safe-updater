# 两类既有方案的匿名化盘点

本文仅保留设计信息；主机名、用户名、域名、IP、仓库账号、会话标识和凭据均未收录。

## 环境 A：Linux Hub + Runner

- systemd user 同时管理 Hub 与 Runner。
- 原更新器由隔日凌晨 timer 触发。
- 已有优点：双重空闲检查、源码补丁、类型检查与构建、API 烟测、失败恢复。
- 已有局限：用户名、CPU 架构和平台二进制路径被硬编码；补丁验证依赖特定源码标记，版本变化后容易触发安全回滚。

## 环境 B：macOS Runner

- HAPI 通过 Apple Silicon Homebrew 的全局 npm 安装运行。
- Runner 与自动更新器分别由 LaunchAgent 管理，Hub 位于另一台设备。
- 原流程包含目录锁、Hub 忙闲查询、源码构建、平台二进制替换、Runner 重连烟测及回滚。
- 原门禁按“上次尝试精确时间 + 48 小时”计算；随机延迟会让第二个日历日差几分钟才满 48 小时，实际推迟到第三天。

## 归并决策

1. 用户名、安装前缀、CPU 架构、角色和服务管理器改为检测或配置。
2. Hub 依据 agent state 判断远程任务，本地依据严格锚定的运行日志判断执行/等待状态。
3. 网页打开、Runner 常驻或会话生命周期为 running，本身不视为任务活跃。
4. 官方包和源码补丁分成两种模式；补丁冲突时在切换前终止。
5. systemd 与 launchd 共用更新核心和时区日历门禁。
6. 完整旧安装树在变更前快照，回滚不依赖软件仓库网络。
