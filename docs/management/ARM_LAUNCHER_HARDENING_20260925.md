## Four repairs

1. **Cooperating-launcher serialization.** A stable per-user Colima `flock` is held from before Docker-client setup until transaction cleanup completes. The lock file is never unlinked; non-regular files, symlinks, wrong ownership, non-0600 mode and extra hard links fail closed. It is independent of checkout/cwd. There are running-container checks before creation and immediately before start. The 1 GiB/no-extra-swap, 0.75 CPU and 128 PID caps remain; the daemon must report at least 2,000,000,000 bytes of total memory. This is not a global Docker lock or a measurement of free host RAM: unrelated clients can still start after the second check. Coordinate a quiet Docker window; no claim of exclusive daemon ownership is made.

2. **Uncertain outcomes and exact owned cleanup.** Ownership label and random dedicated name are generated before `create` is attempted. Even creation timeout/interruption triggers inspection by exact name, full container ID, ownership label and intended image identity. Removal targets the verified immutable container ID, never an unchecked name or wildcard. Absence is verified after removal. A failed create with no visible container remains **cleanup unconfirmed**, because the daemon may complete it later; only generated name/owner identifiers are returned for manual follow-up. Ownership mismatch is never force-deleted. Cleanup is retried once on failure, stays bounded, and failure suppresses PASS.

   Docker CLI processes—including attach—have bounded reads/deadlines and are terminated/reaped on timeout or interruption. SIGTERM/SIGINT unwind through cleanup; additional signals are deferred during cleanup. Uncatchable SIGKILL, host loss or daemon unavailability cannot guarantee removal: the container entry command additionally uses GNU `timeout` (240 seconds, then 5-second kill escalation). This watchdog is only a bounded-lifetime safeguard, not evidence that a container was removed. Unconfirmed cleanup must be reconciled before another test.

3. **No inherited Docker account configuration.** The executable is resolved on a fixed system PATH; every Docker command explicitly selects the local user's Colima Unix socket and a mode-0700 temporary, empty Docker config. CLI environment contains only fixed PATH, temporary HOME and LANG; it does not inherit `DOCKER_CONTEXT`, `DOCKER_HOST`, `DOCKER_CONFIG`, credential-helper configuration, proxy variables or model-account environment. Temporary config is removed after the transaction. Container PATH/HOME/LANG are explicitly overridden; inspected `Config.Env` is checked against a narrow name/value allowlist **before start**, including rejection of injected proxies/unknown keys. The worker retains its independent environment/network/credential-boundary checks.

4. **Typed evidence and post-cleanup final verdict.** Worker output is capped at 16 KiB, parsed without duplicate keys, and must have the exact nine stages in order, exact allowed fields/types/constants, correct protocol, and mode-bound success vs provider-failure semantics. Dynamic values are restricted to bounded integer metrics and two SHA-256 fields. Unknown fields, incomplete/reordered/duplicate stages, legacy markers, malformed/oversized output and wrong test mode fail without echoing raw output. Worker emits `ARM_WORKER_CHAIN_COMPLETE`, not PASS. The host emits one projected terminal verdict only after successful container exit **and verified removal**. No arbitrary Docker stderr, worker JSON or exception message is forwarded.
